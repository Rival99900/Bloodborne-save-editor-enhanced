# Equipment insertion review — local v0.4.1

Reviewed upstream: [84adcfaba099d4d54ba98ae9c069fe77228706e9](https://github.com/Noxde/Bloodborne-save-editor/commit/84adcfaba099d4d54ba98ae9c069fe77228706e9), authored by [valentinoamato](https://github.com/valentinoamato).

The commit adds `Inventory::add_armor_or_weapon` with an `is_storage` argument and tests covering inventory and storage. It changes the Rust data layer, not the Enhanced UI. It creates a 60-byte equipment record and a destination reference, increments both destination counters, and initializes five closed gem slots.

## Reasons it cannot safely replace the current allocator

- `available_offset` starts at zero. If no candidate is found, the function still writes the equipment record there after modifying inventory and counters.
- Sixty consecutive positions failing a structural recognizer are treated as available space. Unrecognized bytes are not evidence of unused save data.
- A full destination advances its boundary without first proving that the following region is free.
- The next handle uses unchecked `u16` addition. Exhaustion is not handled before mutation.
- A fixed header/durability value of 200 is used for every weapon and armor. The existing local allocator uses different templates; neither parser tests nor this commit demonstrate that this resolves the PS4 failures.

Enhanced already has a destination-aware experimental `SaveData::add_direct_equipment_at` implementation and catalog UI routing for both destinations. Its public Tauri command and confirmation button remain disabled because the source records prior PS4 SIGBUS/general-protection failures. Re-enabling the button alone would expose that known failure again.

## Validation needed before enabling

Obtain a controlled save pair where the game itself adds exactly one weapon or armor. Resolve all associated equipment metadata and ownership references, then implement allocation with preflight capacity checks and transaction rollback. Verify inventory and storage independently, including full destinations, multiple additions, duplicate catalog IDs, handle exhaustion, and save/reparse consistency. Finally, confirm normal loading and use of the equipment in-game. Successful Rust parsing alone does not establish game compatibility.

No upstream insertion code was copied or enabled in this revision. Existing replacement and other item operations are preserved. The local UI change concerns only the Flags notification; no GitHub publication was performed.
